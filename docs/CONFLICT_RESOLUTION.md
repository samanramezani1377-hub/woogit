# WooGit — Conflict Resolution

## تصمیم اصلی

استراتژی Conflict Resolution برای Entityهای همزمان، **Field-level Merge** است.

اگر تغییر محلی و تغییر سرور روی فیلدهای متفاوت یک Entity باشند، هر دو تغییر باید تا حد امکان حفظ شوند.

مثال:

```text
Local:  price = 900,000
Server: stock = 12

Result:
price = 900,000
stock = 12
```

اگر هر دو طرف دقیقاً یک فیلد را تغییر داده باشند یا ادغام امن نباشد، Conflict باید به کاربر ارائه شود و WooGit نباید بدون اطلاع کاربر یکی را کورکورانه overwrite کند.

## سه وضعیت

### 1. Auto Merge

تغییرات روی فیلدهای متفاوت هستند → ادغام خودکار.

### 2. User Resolution

تغییرات روی یک فیلد ناسازگار هستند → نمایش Conflict و درخواست انتخاب کاربر.

### 3. Safe Server/Local Rules

برای بعضی فیلدها در آینده می‌توان Rule تخصصی تعریف کرد؛ مثلاً فیلدهایی که ماهیت جمع‌شونده یا وضعیت‌محور دارند. این Ruleها باید قابل توسعه باشند و در Core hard-code نشوند.

## اصل ایمنی

هیچ Conflict مهمی نباید با Last-Write-Wins ساده حل شود، مگر اینکه برای همان Entity/Field صراحتاً Rule تعریف شده باشد.

## UX

Conflict Resolution نباید مسیر عادی سه محور اصلی را کند کند. فقط زمانی UI مربوط به Conflict ظاهر می‌شود که واقعاً تعارض غیرقابل ادغام وجود داشته باشد.

کاربر باید بتواند مقدار Local و Server را ببیند و تصمیم بگیرد. این نمایش به‌صورت یک **مودال** انجام می‌شود که هر دو مقدار را کنار هم نشان می‌دهد. پس از انتخاب، نتیجه به یک Local Change جدید تبدیل می‌شود و دوباره وارد Pending Queue می‌شود تا با همان سیستم Push ثبت و تأیید شود.

## Versioning Integration

Conflict Detection باید با Entity Commit/Version و Pending Queue یکپارچه باشد. نسخه‌ای که کاربر روی آن تغییر داده و نسخه‌ای که سرور در آن قرار دارد باید قابل مقایسه باشند.
