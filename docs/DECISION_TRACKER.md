# ووگیت — پیگیری تصمیم‌ها و پرسش‌ها

این فایل فهرست زنده‌ی تصمیم‌ها و پرسش‌های محصول و معماری است. پیش از طرح هر پرسش جدید باید این فایل بررسی شود تا پرسش تکراری مطرح نشود.

## تصمیم قطعی — نسخه تغییرات سمت فروشگاه در نسخه اول

- [x] در نسخه اول برای تشخیص نسخه/آخرین تغییر هر موجودیت از `date_modified_gmt` ووکامرس استفاده می‌شود.
- [x] این مقدار «نسخه تشخیصی سمت فروشگاه» محسوب می‌شود، نه یک شناسه Commit واقعی و یکتای تاریخچه تغییرات.
- [x] برای هر موجودیت، شناسه موجودیت به‌همراه `date_modified_gmt` به‌عنوان وضعیت نسخه سمت فروشگاه نگهداری می‌شود.
- [x] اگر مقدار `date_modified_gmt` سمت فروشگاه نسبت به وضعیت شناخته‌شده محلی تغییر کرده باشد، برنامه آن را به‌عنوان نسخه جدیدتر تشخیص می‌دهد.
- [x] Commit واقعی و تاریخچه دقیق تغییرات به نسخه‌های آینده، پس از امکان استفاده از افزونه همراه یا سرور اختصاصی، موکول می‌شود.
- [x] این لایه باید طوری طراحی شود که در آینده بتوان `date_modified_gmt` را بدون بازطراحی Core با شناسه Commit واقعی جایگزین یا تکمیل کرد.

## تصمیم قطعی — اعلان سفارش جدید در نسخه اول

- [x] مبنای نسخه اول برای تشخیص سفارش جدید، بررسی دوره‌ای و همگام‌سازی پس‌زمینه‌ای با رابط برنامه‌نویسی ووکامرس است.
- [x] برنامه باید برای اجرای این بررسی‌ها از سازوکارهای رسمی و کم‌مصرف اندروید مانند WorkManager استفاده کند و زمان‌بندی را با محدودیت‌های سیستم‌عامل تطبیق دهد.
- [x] برنامه نباید برای دریافت اعلان، یک اتصال دائمی یا سرویس پس‌زمینه دائمی ایجاد کند.
- [x] در صورت وجود یک سرویس خارجی قابل‌اعتماد که بدون راه‌اندازی سرور اختصاصی ووگیت و بدون افزونه وردپرس بتواند اعلان سفارش جدید را به‌صورت قابل‌اتکا بهتر از بررسی دوره‌ای فراهم کند، در بررسی فنی آینده امکان استفاده از آن بررسی می‌شود.
- [x] استفاده از سرویس خارجی نباید باعث وابستگی اجباری به Backend اختصاصی ووگیت در نسخه اول شود.
- [x] در حال حاضر سرویس‌های اعلان فوری مانند Firebase Cloud Messaging برای ارسال خودکار از سمت فروشگاه به یک محیط مورداعتماد برای ارسال پیام نیاز دارند؛ بنابراین به‌تنهایی جایگزین بررسی دوره‌ای بدون Backend/افزونه نیستند.
- [x] اگر در آینده Backend یا افزونه اضافه شود، معماری اعلان باید بتواند از اعلان Push واقعی استفاده کند، بدون اینکه لایه اصلی تشخیص سفارش بازطراحی شود.
- [x] اطلاعات اعلان سفارش جدید در نسخه اول باید شامل شماره سفارش، مبلغ، تعداد کالا، نام کالاها، تاریخ و ساعت باشد.

## تصمیم قطعی — آمادگی کامل راست‌به‌چپ و چپ‌به‌راست

- [x] نسخه اول فارسی و راست‌به‌چپ است.
- [x] رابط کاربری باید از ابتدا برای تغییر کامل جهت بین راست‌به‌چپ (RTL) و چپ‌به‌راست (LTR) طراحی شود.
- [x] در طراحی رابط کاربری نباید چیدمان به مختصات ثابت چپ/راست وابسته باشد؛ در موارد ممکن از مفاهیم شروع/پایان استفاده شود.
- [x] فاصله‌ها، ترازها، فرم‌ها، فهرست‌ها، منوها، آیکون‌ها و اجزای رابط نباید با تغییر جهت نوشتار به‌هم بریزند.
- [x] انیمیشن‌ها و رفتارهای حرکتی نیز باید با تغییر جهت قابل تطبیق باشند.
- [x] طول متفاوت متن در زبان‌های آینده نباید باعث خراب شدن چیدمان شود.
- [x] اضافه شدن زبان‌های چپ‌به‌راست در آینده نباید نیازمند بازنویسی رابط کاربری یا منطق اصلی باشد.
- [x] ساختار ترجمه باید از ابتدا قابل توسعه برای زبان‌ها و جهت‌های نوشتاری مختلف باشد.

## وضعیت

- `[x]` تصمیم قطعی و در مستندات پروژه ثبت شده است.
- `[ ]` پرسش باز و نیازمند تصمیم کاربر است.
- **مسدودکننده**: موضوعی که پیش از شروع کدنویسی باید حتماً مشخص شود.
- **نیازمند بررسی فنی**: موضوعی که باید با بررسی فنی یا مستندات مشخص شود، نه با حدس.

- [x] اعلان باید حتی با بسته بودن برنامه دریافت شود و اطلاعات اصلی آن شامل شماره سفارش، مبلغ، تعداد کالا، نام کالاها، تاریخ و ساعت باشد.

## پرسش‌های باز و مواردی که باید قبل از کدنویسی تعیین شوند

### پرسش ۰۱ — حل شد

نسخه تغییرات سمت فروشگاه با `date_modified_gmt` مشخص شد. تصمیم نهایی در بالا ثبت شده است.

### پرسش ۰۲ — حل شد

مبنای نسخه اول بررسی دوره‌ای و همگام‌سازی پس‌زمینه‌ای است. امکان استفاده از سرویس خارجی اعلان در صورت پیدا شدن راهکار سازگار با محدودیت‌های نسخه اول در بررسی فنی آینده باز گذاشته شد.

### پرسش ۰۳ — حل شد

عملیات پرتکراری که مستقیماً در صفحه اصلی سفارش (لایه اول) قابل انجام هستند: **تغییر وضعیت سفارش** و **افزودن/مشاهده یادداشت سریع**. سایر عملیات (تغییر اطلاعات مشتری، آدرس، اقلام، تخفیف، هزینه حمل، روش پرداخت، اطلاعات ارسال/رهگیری و غیره) در «ویرایش کامل سفارش» باقی می‌مانند.

### پرسش ۰۴ — حل شد

تمام فیلدهای «ویرایش کامل سفارش» (لایه دوم) در نسخه اول فعال هستند: تغییر اطلاعات مشتری، تغییر آدرس، تغییر اقلام و تعداد، تخفیف‌ها، هزینه حمل، روش پرداخت، اطلاعات ارسال/رهگیری و یادداشت‌ها. هیچ‌کدام به نسخه‌های بعدی موکول نمی‌شوند.

### پرسش ۰۵ — حل شد

- محصول متغیر (Variable Product) و Variationها: پشتیبانی **کامل** از V1 — ساخت، ویرایش و حذف محصول متغیر و Variationهای آن (نه فقط مشاهده).
- ویژگی‌ها (Attributes): پشتیبانی **کامل** از V1 — هم ویژگی‌های سفارشی (Custom) مخصوص یک محصول و هم ویژگی‌های سراسری (Global attributes) قابل استفاده در چند محصول.
- محصول ساده (Simple Product) نیز کامل پشتیبانی می‌شود (طبق ORDERS_AND_PRODUCTS.md).
- موجودی (Stock)، دسته‌بندی‌ها و تصاویر برای هر دو نوع محصول (ساده و متغیر) در V1 فعال هستند.

### پرسش ۰۶ — حل شد

- محدودیت تعداد/حجم گالری تصاویر: **بدون محدودیت خاص از سمت اپ**؛ فقط محدودیت طبیعی حافظه دستگاه و شبکه اعمال می‌شود.
- فشرده‌سازی/تغییر اندازه: تصویر **بدون تغییر و با کیفیت اصلی** آپلود می‌شود؛ اپ پیش از آپلود آن را فشرده یا کوچک نمی‌کند.
- بارگذاری، تلاش مجدد (Retry) و مدیریت اینترنت ضعیف طبق اصول عمومی `OFFLINE_QUEUE_AND_PUSH.md` و `OFFLINE_AND_RESILIENCE.md` انجام می‌شود (صف Pending، Retry با تأخیر، عدم گم‌شدن تغییر).

### پرسش ۰۷ — حل شد

- حذف محصول: **فعال در V1** (از طریق WooCommerce API؛ رفتار پیش‌فرض ووکامرس معمولاً انتقال به زباله‌دان/Trash است که امکان بازیابی را فراهم می‌کند).
- حذف/لغو سفارش: **فعال در V1** — هم لغو سفارش (تغییر وضعیت به Cancelled) و هم حذف واقعی سفارش پشتیبانی می‌شود.
- هر دو عملیات باید مانند سایر تغییرات از مدل Local-first/Commit/Pending Queue پیروی کنند.

### پرسش ۰۸ — چند دستگاه و دسترسی در آینده

نسخه اول تک‌دستگاه و تک‌نقش است؛ برای آینده باید مدل هویت دستگاه، هویت کاربر و محدوده دسترسی نهایی شود. فعلاً این پرسش فعال نیست و تا رسیدن به مرحله طراحی آن بخش مطرح نمی‌شود.

### پرسش ۰۹ — حل شد

- **به‌روزرسانی اپ (همان دستگاه):** دیتابیس محلی و صف عملیات معلق باید **حفظ شوند**؛ نصب نسخه جدید نباید داده یا صف Pending را پاک کند.
- **تعویض/فرمت گوشی:** بازیابی خودکار دیتابیس/صف از طریق بک‌آپ ابری گوگل (Android Auto Backup) انجام **نمی‌شود**. داده محلی و صف عملیات معلق فقط روی همان دستگاه باقی می‌مانند و با تعویض/فرمت گوشی از بین می‌روند؛ کاربر باید مجدداً اتصال فروشگاه را برقرار کند تا داده از سرور واکشی شود.
- این تصمیم با سیاست امنیتی `SECURITY_AND_AUTH.md` هم‌راستاست: Consumer Key/Secret در هیچ حالتی (نه در بک‌آپ محلی نصب/آپدیت و نه در بک‌آپ ابری) نباید به‌صورت غیرامن منتقل شوند؛ در صورت استفاده از هر مکانیزم بک‌آپ اندرویدی، Credentialهای ذخیره‌شده در Keystore باید صریحاً از دامنه‌ی بک‌آپ مستثنی شوند.

### پرسش ۱۰ — حل شد

در نسخه اول کاربر فقط وضعیت ساده‌ی هر تغییر را می‌بیند: **معلق (Pending) / همگام‌شده (Synced) / ناموفق (Failed)**. تاریخچه کامل تغییرات (Change Log/Audit Trail) به آینده موکول می‌شود و در V1 پیاده‌سازی نمی‌شود.

### پرسش ۱۱ — مدیریت خطا

باید دسته‌بندی خطاهای شبکه، احراز هویت، سطح دسترسی، اعتبارسنجی، تعارض و خطای سرور و تجربه کاربری هرکدام نهایی شود.

### پرسش ۱۲ — آزمایش و تحویل خودکار

قبل از کدنویسی باید سطح آزمایش اجباری نسخه اول مشخص شود: آزمایش واحد، آزمایش یکپارچه، آزمایش قرارداد رابط برنامه‌نویسی، آزمایش همگام‌سازی و صف، آزمایش رابط کاربری و آزمایش شبکه ناپایدار.

### پرسش ۱۳ — مشخصات رابط کاربری و تجربه کاربری

باید مشخص شود قبل از کدنویسی، جریان‌ها و صفحه‌های نسخه اول تا چه سطحی مستند یا طراحی شوند تا هسته و تجربه کاربری با هم تناقض نداشته باشند.

## قوانین این فهرست

۱. هر بار کاربر به یک پرسش پاسخ می‌دهد، همان پرسش باید در همین فایل `[x]` شود و تصمیم نهایی در سند اصلی مربوط ثبت یا به‌روزرسانی و ارسال شود.
۲. اگر پرسش جدیدی از بررسی معماری، محدودیت رابط برنامه‌نویسی ووکامرس، اندروید یا نیاز محصول به‌وجود آمد، با شماره بعدی اضافه شود.
۳. پرسش تکراری ممنوع است؛ قبل از پرسیدن، این فایل و سند اصلی مرتبط بررسی شود.
۴. اگر پاسخ کاربر باعث تغییر تصمیم قبلی شود، سند قبلی باید به‌روزرسانی شود؛ هیچ چیزی بدون تصمیم صریح حذف نشود.
۵. موارد مسدودکننده باید قبل از شروع پیاده‌سازی هسته تعیین تکلیف شوند.
