# WooGit — Decision & Question Tracker

این فایل فهرست زنده‌ی تصمیم‌ها و سؤال‌های محصول/معماری است. قبل از سؤال جدید باید این فایل بررسی شود تا سؤال تکراری پرسیده نشود.

## وضعیت

- `[x]` تصمیم قطعی و در مستندات پروژه ثبت شده
- `[ ]` سؤال باز / نیازمند تصمیم کاربر
- `BLOCKER` موضوعی که قبل از کدنویسی باید حتماً روشن شود
- `DISCOVERY` موضوعی که باید با بررسی فنی/مستندات مشخص شود، نه با حدس

## تصمیم‌های قطعی

- [x] سه محور اصلی: اعلان سفارش جدید، سفارش‌ها، مدیریت محصولات.
- [x] قابلیت‌های قبلی حذف نمی‌شوند و در اولویت‌های بعدی باقی می‌مانند.
- [x] اعلان سفارش جدید بالاترین فوریت را دارد؛ هدف مقیاس دقیقه و حداکثر قابل‌قبول حدود یک ساعت.
- [x] اعلان باید حتی با بسته بودن اپ دریافت شود و اطلاعات اصلی شامل شماره سفارش، مبلغ، تعداد کالا، نام کالاها، تاریخ و ساعت باشد.
- [x] تغییرات وضعیت سفارش برای آینده آماده می‌شوند و V1 محور اصلی اعلانش فقط سفارش جدید است.
- [x] داشبورد V1 فقط تعداد سفارش‌های جدید را نشان می‌دهد.
- [x] سفارش: اطلاعات مهم در صفحه اصلی و جزئیات کامل/کم‌کاربردتر در Edit Order.
- [x] محصول: جستجوی Product از V1 لازم است؛ Global Search برای آینده است.
- [x] افزودن محصول یک جریان واحد Quick-to-Full است؛ فقط نام اجباری است و تصویر اصلی مهم ولی اختیاری است.
- [x] V1 بدون Backend اختصاصی است.
- [x] V1 اتصال مستقیم به WooCommerce REST API دارد.
- [x] Companion Plugin به نسخه‌های آینده موکول شده است.
- [x] احراز هویت باید با امنیت متناسب، Secure Storage/Keystore، HTTPS و عدم نشت Credential انجام شود.
- [x] کاربر برای اتصال محوری با Store URL + Consumer Key + Consumer Secret کار می‌کند.
- [x] V1 یک Store است؛ Core برای Multi-Store آماده است.
- [x] V1 یک دستگاه و یک نقش/سطح دسترسی است.
- [x] آینده: چند کاربر/چند دستگاه، با استقلال هر دستگاه.
- [x] اینترنت ضعیف/قطع کوتاه نباید اپ را از کار بیندازد؛ Pending Queue، Retry/Backoff و ادامه پس از اتصال لازم است.
- [x] V1 کاملاً Offline نیست، ولی Core باید برای Offline کامل آینده آماده باشد.
- [x] داده‌های مفید سفارش/محصول Local Cache می‌شوند؛ Credentialها جدا و امن نگهداری می‌شوند.
- [x] هر Entity تغییرکرده Commit/Version خودش را افزایش می‌دهد.
- [x] تغییر Local بلافاصله UI را به‌روز می‌کند و سپس برای Sync وارد Pending Queue می‌شود.
- [x] اگر Sync شکست خورد، تغییر از بین نمی‌رود و بعداً Push می‌شود.
- [x] Conflict آینده: ابتدا Field-level/Auto Merge؛ اگر امن و قابل ادغام نبود، User Resolution.
- [x] Future User Tracker، Live Notification Center و AI/Site Assistant باید از ابتدا مرز معماری داشته باشند، اما V1 فعالشان نمی‌کند.

## سؤال‌های باز / مواردی که باید قبل از کدنویسی تعیین شوند

### Q01 — BLOCKER — Server-side Change Version بدون Plugin

با تصمیم V1 بدون Companion Plugin، باید مشخص کنیم «شماره نسخه/Commit سمت فروشگاه» را دقیقاً چگونه به‌دست می‌آوریم.

گزینه‌های فعلی:
- `[ ]` استفاده از `date_modified_gmt` / timestampهای موجود WooCommerce به‌عنوان نسخه تقریبی.
- `[ ]` مکانیزم دیگری فقط با REST API موجود، در صورت وجود راه قابل اتکا.
- `[ ]` Commit دقیق سراسری را به آینده و بعد از اضافه شدن Plugin/Backend موکول کنیم و در V1 فقط Per-Entity Local/Server state داشته باشیم.

### Q02 — BLOCKER — Push سفارش جدید در V1 بدون Backend و Plugin

باید مشخص کنیم با توجه به محدودیت Android و REST API، چه سطحی از «اعلان سریع حتی در حالت بسته» را در V1 تضمین می‌کنیم. REST API به‌تنهایی Event Push به گوشی ایجاد نمی‌کند.

- `[ ]` V1 بدون Backend/Plugin: Background polling/sync با محدودیت‌های Android؛ هدف best-effort.
- `[ ]` یک راهکار Push خارجی که بدون Backend اختصاصی قابل استفاده باشد، در صورت اثبات فنی.
- `[ ]` اعلان واقعی server-driven را رسماً به نسخه آینده موکول کنیم و V1 فقط detection پس‌زمینه‌ای داشته باشد.

این سؤال باید با بررسی فنی سرویس‌های Push و محدودیت‌های Android پاسخ داده شود، نه با حدس.

### Q03 — عملیات دقیق صفحه اصلی سفارش V1

مشخص است اطلاعات مهم روی صفحه اصلی باشند و عملیات پرتکرار هم همان‌جا انجام شوند؛ باید فهرست دقیق عملیات را نهایی کنیم.

### Q04 — فهرست دقیق فیلدهای قابل ویرایش سفارش در V1

باید تعیین شود کدام عملیات Edit Order واقعاً در V1 فعال باشند و کدام فقط برای آینده آماده شوند.

### Q05 — فهرست دقیق قابلیت‌های محصول V1

REST API چه فیلدها/نوع‌های محصول/Variationها را در V1 باید پوشش دهد؟ مخصوصاً Simple، Variable، Attributes، Variations، Inventory، Categories و Images.

### Q06 — تصاویر محصول

حد و رفتار Cache، Resize/Compression، Upload/Retry و مدیریت چند تصویر باید نهایی شود؛ مخصوصاً برای اینترنت ضعیف.

### Q07 — حذف محصول و سفارش

باید مشخص شود Delete در V1 فعال است یا فقط Edit/Create و حذف به آینده موکول می‌شود؛ همچنین Undo/Recovery در صورت فعال بودن Delete.

### Q08 — چند دستگاه و دسترسی در آینده

V1 تک‌دستگاه/تک‌نقش است؛ برای آینده باید بعداً مدل Device Identity، User Identity و Permission Scope نهایی شود. فعلاً سؤال فعال نیست و تا رسیدن به مرحله طراحی آن بخش پرسیده نمی‌شود.

### Q09 — Backup / Migration

باید مشخص شود Local DB و Pending Queue هنگام آپدیت اپ، پاک شدن داده، Restore یا تعویض گوشی چه سیاستی دارند.

### Q10 — Git/Commit Sync UI

باید نهایی شود کاربر در V1 چه مقدار از وضعیت Commit/Push را ببیند: فقط Pending/Synced/Failed یا جزئیات کامل History هم لازم است.

### Q11 — Error Handling

باید دسته‌بندی خطاهای Network، Auth، Permission، Validation، Conflict و Server Error و UX هرکدام نهایی شود.

### Q12 — تست و CI/CD

قبل از کدنویسی باید سطح تست اجباری V1 مشخص شود: Unit، Integration، REST contract، Sync/Queue، UI و تست شبکه ناپایدار.

### Q13 — UI/UX Specification

باید مشخص شود قبل از کدنویسی UI، Flow و Screenهای V1 تا چه سطحی مستند/طراحی شوند تا Core و UX متناقض نشوند.

## قوانین این Tracker

1. هر بار کاربر به یک سؤال جواب می‌دهد، همان سؤال باید در همین فایل `[x]` شود و تصمیم نهایی در سند اصلی مربوط ثبت/به‌روزرسانی و Push شود.
2. اگر سؤال جدیدی از بررسی معماری، محدودیت REST API، Android یا نیاز محصول به‌وجود آمد، با شماره بعدی اضافه شود.
3. سؤال تکراری ممنوع است؛ قبل از پرسیدن، این فایل و سند اصلی مرتبط بررسی شود.
4. اگر پاسخ کاربر باعث تغییر تصمیم قبلی شود، سند قبلی باید به‌روزرسانی شود؛ چیزی بدون تصمیم صریح حذف نشود.
5. `BLOCKER`ها باید قبل از شروع پیاده‌سازی Core تعیین تکلیف شوند.
