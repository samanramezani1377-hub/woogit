# WooGit — Roadmap

این سند مرجع اصلی اولویت‌بندی نسخه‌هاست: چه چیزی در V1 فعال است، چه چیزی فقط از نظر معماری آماده می‌شود و چه چیزی به نسخه‌های بعدی موکول شده است.

> **قانون Future:** قابلیت آینده باید از امروز در مرزهای معماری قابل پذیرش باشد، اما تا زمانی که در این سند برای نسخه فعلی فعال نشده، نباید به V1 وارد شود یا مسیر اصلی محصول را پیچیده کند.

## V1 — هسته محصول

هدف V1 ساخت یک هسته واقعی، سریع، پایدار و قابل اتکا برای یک فروشگاه WooCommerce است؛ نه فعال کردن تمام قابلیت‌های آینده.

### سه محور غیرقابل حذف

1. **اعلان سفارش جدید** — بالاترین فوریت؛ تشخیص سفارش جدید با سازوکار پس‌زمینه و REST ووکامرس، بدون Backend اختصاصی.
2. **مشاهده و مدیریت سفارش** — خلاصه سریع، جزئیات کامل و عملیات مدیریتی موردنیاز.
3. **مدیریت محصولات** — افزودن و ویرایش سریع در یک جریان واحد، همراه با مدیریت کامل محصول، محصول متغیر و Variationها.

### قابلیت‌های V1

- اتصال مستقیم به WooCommerce با آدرس فروشگاه و Consumer Key/Secret.
- Local-first / Offline-first و Optimistic UI.
- Pending Queue پایدار، Retry، Timeout و Conflict Handling.
- Push تغییرات محلی به WooCommerce بدون وابستگی به Backend اختصاصی.
- نسخه تشخیصی سمت فروشگاه با `date_modified_gmt`؛ نه Commit واقعی.
- داشبورد ساده و عملیاتی با تمرکز بر تعداد سفارش‌های جدید.
- مدیریت سفارش و ویرایش کامل سفارش.
- تغییر وضعیت و یادداشت سریع سفارش.
- لغو و حذف سفارش.
- مدیریت کامل محصول، شامل محصول ساده و متغیر و Variationها.
- Attributes سفارشی و سراسری.
- تصویر اصلی و گالری با کیفیت اصلی طبق تصمیم V1.
- حذف محصول.
- جستجوی محصول.
- RTL فارسی از ابتدا، با ساختار آماده برای LTR و زبان‌های آینده.
- وضعیت Sync ساده: Pending / Synced / Failed.
- Status Dot اتصال/Sync و رفتار خطاهای تعریف‌شده در Decision Tracker.
- Unit، Integration و UI Test و تست اجباری شبکه ناپایدار/کند.
- Hi-Fi Design و Design System کامل پیش از شروع کدنویسی.

### اصول V1

- V1 برای **یک فروشگاه** طراحی می‌شود.
- V1 **Backendless** است؛ WooCommerce خود Backend اصلی است.
- افزونه همراه WordPress برای Commit واقعی یا Endpoint اختصاصی در V1 ساخته نمی‌شود.
- اتصال دائمی پس‌زمینه برای اعلان مجاز نیست.
- قابلیت‌های آینده نباید باعث کند شدن Launch، سفارش یا افزودن/ویرایش محصول شوند.

## بعد از V1 — آماده‌سازی و گسترش کنترل‌شده

این موارد باید در Core مرزبندی شده باشند، اما فعال‌سازی آن‌ها به نیاز و تصمیم نسخه بعدی وابسته است:

- Commit واقعی و تاریخچه دقیق تغییرات با Companion Plugin یا Backend مناسب.
- Push Notification واقعی با Provider مناسب، بدون تغییر Notification Domain.
- Notification Center و Eventهای بیشتر.
- تغییر وضعیت‌های مهم سفارش، پرداخت، لغو، Sync و رویدادهای محصول به‌عنوان Event/Notification.
- Multi-Store کامل.
- تجمیع سفارش‌های چند فروشگاه در داشبورد با Store Source و Deep Link صحیح.
- قابلیت‌های پیشرفته User/Event Tracking با رعایت حریم خصوصی.
- iOS با استفاده از Core مشترک KMP.
- AI / Assistant برای کار با Orders، Products، Store Data و Eventها.
- Billing / Productization و مدل‌های تجاری.
- انتخاب و فعال‌سازی مسیرهای پرداخت و کانال‌های توزیع مناسب.

## قابلیت‌هایی که فعلاً فقط باید آماده باشند

- `ai` / `assistant` boundary
- Event-driven Core و Event subscriptions
- Notification provider abstraction
- Multi-Store Store-scoped architecture
- Commit Provider abstraction برای جایگزینی `date_modified_gmt`
- LTR و چندزبانه شدن
- iOS/KMP
- Billing و License abstraction

## قواعد تغییر Roadmap

1. هیچ قابلیت موجود بدون تصمیم صریح حذف نمی‌شود.
2. تصمیم جدید باید ابتدا در `docs/DECISION_TRACKER.md` ثبت شود.
3. جزئیات فنی در سند تخصصی خودشان قرار می‌گیرند؛ Roadmap فقط اولویت و وضعیت فعال‌سازی را تعیین می‌کند.
4. تغییر Roadmap باید با یک Commit جدا و پیام واضح ثبت شود.
5. اگر قابلیت آینده‌ای برای V1 ضروری شد، ابتدا باید اثر آن روی Product Vision و Architecture مشخص و سپس تصمیم ثبت شود.
