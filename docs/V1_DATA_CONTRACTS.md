# WooGit V1 — Data, Sync and Conflict Contracts

## 1. V1 backend boundary

There is **no WooGit backend/server in V1**. The only remote system is the merchant's existing WooCommerce REST API. No custom push service, cloud database, WooGit API, websocket server or hosted file storage is required for V1.

## 2. Local data ownership

Local database is the source of truth for the app UI. Remote WooCommerce is the source of truth for server state after successful synchronization.

Required local concepts:

- Store
- Order
- OrderItem
- Customer
- Address
- Payment
- Shipping
- Product
- ProductImage
- ProductAttribute
- Variation
- PendingOperation
- EntityVersion
- Conflict
- SyncMetadata

## 3. Versioning

V1 uses WooCommerce `date_modified_gmt` as the lightweight server version signal. A future WooGit companion plugin/server version provider is out of V1 scope.

Each synchronized entity stores:

- entity id
- store id
- local version
- last known server version
- last synced timestamp
- sync status

## 4. Freshness states

```text
NEVER_SYNCED
FRESH
STALE
SYNCING
OFFLINE
```

The UI must expose enough information for the user to understand whether displayed data is cached/stale.

## 5. Pending operation states

```text
PENDING -> RUNNING -> SUCCEEDED
                   -> RETRYABLE_FAILURE -> PENDING
                   -> PERMANENT_FAILURE
                   -> CONFLICT
```

A persisted operation must survive process death and app restart.

## 6. Operation identity and idempotency

Every mutation gets a stable local `operationId` and deterministic operation payload hash. The queue must never create a second logical operation merely because the first network attempt timed out.

V1 cannot assume that WooCommerce itself provides an application-level idempotency key for every mutation. Therefore the client must:

1. persist operation before network execution;
2. keep the operation identity stable across retries;
3. reconcile the server state after ambiguous timeout/failure before issuing a potentially duplicating mutation when practical;
4. mark ambiguous operations as requiring reconciliation rather than blindly repeating unsafe mutations.

## 7. Conflict detection

Before a mutation, compare the local entity's last known `date_modified_gmt` with the current remote version when a remote check is required. A changed remote version means the local mutation is stale and enters `CONFLICT` instead of silently overwriting the server.

## 8. Conflict contract

Conflict record contains:

- store id
- entity type/id
- operation id
- local snapshot
- server snapshot
- base snapshot/version
- conflicting fields
- created timestamp
- resolution state

V1 resolution options:

- Keep server
- Keep local
- Cancel/leave unresolved

Field-level automatic merge is allowed only where explicitly proven safe. Otherwise the conflict remains user-resolvable. No silent overwrite is permitted.

## 9. Offline policy

Read operations use cached local data whenever available. Mutations are written locally first and queued for remote synchronization.

When offline:

- reads show cached data;
- writes remain pending;
- user sees pending state;
- retry happens after connectivity is available;
- failures remain inspectable.

Each error must define retryability and UI recovery behavior.

## 11. Credential lifecycle

```text
INPUT -> VALIDATE -> SECURE_STORE -> REQUEST
                     |                |
                     |                +-> AUTH_FAILURE
                     |
                     +-> DISCONNECT -> DELETE_SECRET
```

Consumer credentials are stored only in platform secure storage. They are excluded from ordinary database records, logs, analytics and crash payloads.

## 12. Notification boundary

V1 has no server push. New-order detection uses Android background scheduling and WooCommerce polling. Notifications are local notifications generated by the app.

Notification identity must be based on store + order identity + detected server state so app restart does not generate duplicates.

## 13. Images

V1 does not introduce a WooGit image server. Product images are read/written through WooCommerce. Local temporary files may be used for safe upload/retry handling.
