# WooGit

اپلیکیشن اندرویدی اختصاصی برای مدیریت سریع و آفلاین‌محور فروشگاه‌های ووکامرس، با مدل همگام‌سازی شبیه به `git push`.

---

## پرامپت پروژه (Project Prompt)

> این بخش یک شرح کامل و دقیق از چیزی است که باید ساخته شود. هر بار که قرار است روی این پروژه (توسط انسان یا مدل هوش مصنوعی) کار شود، باید این پرامپت به‌طور کامل خوانده شود.

> **قاعده‌ی تفسیر «آینده» در این سند:** هر جا در این پرامپت یا در جلسات بعدی گفته شود که قابلیتی «در آینده» اضافه می‌شود، منظور این است که **هسته (Core) باید از همین حالا برای پذیرفتن آن قابلیت آماده و باز طراحی شده باشد** (مثلاً ماژول جدا، لایه‌ی انتزاعی، اینترفیس مشخص)، اما **پیاده‌سازی و فعال‌سازی واقعی آن قابلیت به نسخه‌های بعدی موکول می‌شود** و بخشی از نسخه‌ی یک نیست.

### ۱. مشکل اصلی

اپلیکیشن‌های موجود برای مدیریت ووکامرس روی اندروید (اپ رسمی WooCommerce/WordPress، و اپ‌های ثالث مثل Hippoo) کند، سنگین، و از نظر تجربه‌ی کاربری ضعیف هستند. هدف ساخت یک اپلیکیشن اختصاصی، سریع و ساده است که دقیقاً مطابق نیاز واقعی مدیریت یک فروشگاه ساخته شده باشد، نه یک ابزار همه‌کاره‌ی شلوغ.

### ۲. سه محور اصلی محصول و الگوی استفاده

WooGit قرار نیست صرفاً یک اپ دیگر برای مشاهده‌ی WooCommerce باشد. هدف اصلی آن ساخت یک ابزار مدیریتی سریع و تخصصی برای صاحب فروشگاه است تا برای سه کار اصلی فروشگاه، تا جای ممکن از پنل WordPress/WooCommerce بی‌نیاز شود.

**سه محور زیر هسته و اصل محصول هستند و نباید به‌عنوان قابلیت‌های فرعی یا قابل حذف در نظر گرفته شوند:**

1. **اعلان سفارش جدید — محور فوری (Immediate):** اولین و فوری‌ترین نقطه‌ی تماس کاربر با WooGit. کاربر باید حتی وقتی برنامه کاملاً بسته است، در سریع‌ترین زمان ممکن از ثبت سفارش جدید مطلع شود. هدف عملی این قابلیت اطلاع‌رسانی در مقیاس دقیقه است و در بدترین حالت قابل‌قبول نباید به تأخیری بیشتر از حدود یک ساعت وابسته باشد.
2. **مشاهده و مدیریت سفارش — محور نیاز معمول و روزانه (Hourly / Daily):** پس از دریافت اعلان، کاربر باید بتواند سفارش را داخل برنامه بررسی و مدیریت کند. این بخش ممکن است از چند بار در روز تا استفاده‌ی ساعتی یا روزانه مورد نیاز باشد و باید تا جای ممکن جایگزین پنل سفارشات WordPress/WooCommerce شود.
3. **افزودن و اصلاح محصولات — محور کم‌فوریت‌تر اما سرعت‌محور (Daily / Weekly / On-demand):** این بخش ممکن است برای کاربر روزانه، چند بار در هفته یا فقط هفته‌ای یک‌بار مورد استفاده قرار بگیرد. اما هر زمان کاربر به آن نیاز دارد، کار باید با سریع‌ترین زمان ممکن، کمترین تعداد لمس و کمترین اصطکاک انجام شود. هدف این بخش نیز بی‌نیازی عملی از مدیریت محصولات در پنل WordPress است.

این سه محور فوریت یکسانی ندارند؛ بنابراین **فوریت، زمان پاسخ، UX، اعلان، همگام‌سازی و اولویت منابع باید متناسب با الگوی واقعی استفاده‌ی هر محور طراحی شوند.**

#### اصل اولویت سه محور

- **سفارش جدید:** بالاترین فوریت؛ اطلاع‌رسانی سریع و قابل‌اعتماد حتی در حالت کاملاً بسته‌ی اپ.
- **سفارش‌ها:** نیاز معمول و روزانه؛ دسترسی سریع به خلاصه، جزئیات کامل و عملیات مدیریتی.
- **محصولات:** فوریت پایین‌تر نسبت به دو محور اول، اما سرعت انجام کار در لحظه‌ی نیاز باید بسیار بالا باشد.

### ۳. اولویت‌های بعدی پروژه

سه محور بالا اصل محصول هستند. تمام قابلیت‌ها و تصمیم‌هایی که پیش‌تر در پروژه تعریف شده‌اند **حذف نمی‌شوند**؛ بلکه در رده‌ی اهمیت و الزامات بعدی قرار می‌گیرند و باید در معماری از ابتدا برای آن‌ها آماده بود.

۱. **سرعت اصلاح و افزودن محصول جدید** — معیار اصلی موفقیت در محور سوم است. باز کردن اپ، افزودن یا ویرایش یک محصول، باید در کمترین زمان و کمترین تعداد لمس ممکن انجام شود.

۲. **حداکثر کار در داخل خود اپ** — هدف معماری این است که کاربر برای سه محور اصلی و عملیات مرتبط با آن‌ها، تا جای ممکن نیاز به باز کردن مرورگر یا پنل وردپرس نداشته باشد.

۳. **مدل همگام‌سازی شبیه به `git push`** — تمام تغییرات (محصول جدید، ویرایش، تغییر موجودی/قیمت، تغییر وضعیت سفارش) ابتدا **به‌صورت محلی و آفلاین** ذخیره و در UI فوراً اعمال می‌شوند (Optimistic UI). سپس با یک حرکت (خودکار در پس‌زمینه یا با یک دکمه‌ی صریح شبیه "Push") تمام تغییرات ذخیره‌شده یک‌جا به ووکامرس ارسال می‌شوند. کاربر نباید منتظر پاسخ سرور برای هر تغییر کوچک بماند.

۴. **سرعت اجرای اپ در حد اپ‌های بسیار سریع و بهینه‌ی بازار** — تجربه‌ی کاربری باید native و روان باشد، بدون تأخیر، بدون لگ، شبیه بهترین اپ‌های موجود در Google Play از نظر سرعت رندر و پاسخ‌دهی.

۵. **قابلیت تبدیل بعدی به یک محصول تجاری (Productization)** — معماری باید از ابتدا به‌گونه‌ای طراحی شود که بتوان بعداً:
   - آن را برای چندین فروشگاه/چندین کاربر عرضه کرد
   - یک مدل **Freemium/Premium** پیاده‌سازی کرد (برخی امکانات رایگان، برخی پولی)
   - بدون بازنویسی اساسی، مقیاس‌پذیر باشد

### ۴. معماری فنی پیشنهادی

**اصل بنیادین: ساخت از «هسته» به بیرون (Core-Out Architecture).**
پروژه نباید مستقیم از UI اندروید شروع شود. باید یک **هسته‌ی مشترک (Core Module)** مستقل از پلتفرم ساخته شود که شامل تمام منطق تجاری، مدل‌های دامنه، موتور همگام‌سازی (Sync Engine)، صف تغییرات، و ارتباط با REST API ووکامرس باشد. لایه‌های بیرونی (UI اندروید، و بعداً UI آی‌فون) فقط مصرف‌کننده‌ی این هسته هستند. مزیت این رویکرد:
- وقتی هسته آپدیت یا اصلاح می‌شود (باگ‌فیکس، قابلیت جدید، بهبود موتور Sync)، این تغییر خودکار به تمام پلتفرم‌ها می‌رسد.
- افزودن قابلیت‌های آینده (پشتیبانی هوش مصنوعی، گیت‌وی‌های پرداخت جدید، منطق جدید کسب‌وکار) در هسته انجام می‌شود و تنها یک بار پیاده‌سازی می‌شود.

- **رویکرد Multiplatform:** به‌جای نوشتن هسته فقط برای اندروید، از **Kotlin Multiplatform (KMP)** استفاده شود. لایه‌ی هسته (دامنه، شبکه، دیتابیس محلی، موتور Sync) با KMP نوشته می‌شود تا هم اندروید و هم (در آینده) iOS بتوانند مستقیماً از همان کد استفاده کنند، بدون بازنویسی منطق تجاری. این دقیقاً همان آماده‌بودن برای iOS است که خواسته شده — فعلاً فقط لایه‌ی UI اندروید (Compose) روی این هسته ساخته می‌شود؛ لایه‌ی UI iOS (SwiftUI) هر وقت لازم شد بدون دست‌زدن به هسته اضافه می‌شود.
- **UI اندروید:** Jetpack Compose (Material 3) — با تم اختصاصی «Liquid Glass» (بخش ۹)
- **معماری لایه‌ای:** Clean Architecture (Core مشترک KMP + لایه‌ی Presentation مخصوص هر پلتفرم)، مشابه رویکرد پروژه‌ی ZeroGram اما با جداسازی سخت‌گیرانه‌تر هسته از UI
- **دیتابیس محلی/صف تغییرات:** SQLDelight یا Room با پشتیبانی KMP — تمام تغییرات کاربر ابتدا اینجا ذخیره می‌شوند (منبع حقیقت آفلاین)
- **ارتباط شبکه:** Ktor Client (سازگار با KMP) برای صحبت با REST API ووکامرس (`wp-json/wc/v3/...`)
- **همگام‌سازی پس‌زمینه:** WorkManager در اندروید (فراخوانی منطق Sync از هسته‌ی مشترک)
- **تزریق وابستگی:** Koin یا Hilt (بسته به سازگاری با KMP)
- **Async:** Kotlin Coroutines & Flow
- **ماژول جداگانه برای هوش مصنوعی:** از همین ابتدا یک ماژول (حتی خالی/placeholder) به اسم `ai` یا `assistant` در نظر گرفته شود تا وقتی قابلیت‌های هوش مصنوعی (مثلاً پیشنهاد قیمت، تولید توضیحات محصول، تحلیل فروش) اضافه شدند، به هسته‌ی اصلی وصل شوند بدون تغییر ساختار کلی.
- بدون نیاز به سرور اختصاصی برای هسته‌ی اصلی — خود وردپرس/ووکامرس نقش بک‌اند را دارد. (سرور جدا فقط برای لایسنس/پرمیوم طبق بخش ۸)

### ۵. مکانیزم نسخه‌بندی داده (Data Versioning / «شماره کامیت»)

> این مکانیزم بخشی از هسته‌ی نسخه‌ی یک است، نه یک قابلیت آینده — چون مستقیماً به سرعت، آفلاین‌بودن و تجربه‌ی کاربری پروژه وابسته است.

ایده: یک شماره‌ی نسخه‌ی سراسری (شبیه به شماره‌ی کامیت در گیت) برای داده‌های فروشگاه نگه‌داری شود:

- هر بار داده‌ای در سایت تغییر می‌کند (چه از طریق خود اپ، چه از پنل وردپرس، چه از هر منبع دیگری)، یک شماره‌ی نسخه‌ی سراسری در سمت سرور **بالا می‌رود**.
- اپ همیشه آخرین شماره‌نسخه‌ای که خودش دارد را به‌همراه داده‌ها به‌صورت محلی (کاملاً داخل گوشی) ذخیره می‌کند. تمام صفحات اپ از همین داده‌ی محلی خوانده می‌شوند، نه مستقیم از سایت.
- در دو لحظه، اپ فقط **شماره‌ی نسخه** را از سایت می‌پرسد (یک درخواست بسیار سبک، نه کل داده):
  1. در پس‌زمینه، حتی وقتی اپ بسته است (با WorkManager/کارهای دوره‌ای)
  2. لحظه‌ی باز شدن اپ (یا حتی کمی قبل از باز شدن کامل، اگر پلتفرم اجازه دهد)
- اگر شماره‌نسخه‌ی سرور با نسخه‌ی محلی یکسان بود → هیچ داده‌ای از سایت لود نمی‌شود، همان داده‌ی محلی نمایش داده می‌شود.
- اگر شماره‌نسخه فرق داشت → همگام‌سازی داده (کامل یا فقط بخش تغییریافته) در پس‌زمینه انجام می‌شود، و پس از اتمام، شماره‌نسخه‌ی محلی هم به‌روزرسانی می‌شود.
- وقتی خود اپ تغییری را «Push» می‌کند، بعد از موفقیت‌آمیز بودن ارسال، هم سرور شماره‌نسخه را بالا می‌برد و هم اپ نسخه‌ی محلی‌اش را هم‌گام با آن به‌روزرسانی می‌کند — دقیقاً مثل رفتار `commit` در گیت.

**نکته‌ی پیاده‌سازی:** خود API استاندارد ووکامرس چنین شماره‌ی سراسری‌ای ندارد (فقط `date_modified` روی هر آیتم دارد). دو مسیر ممکن است:
1. **راه ساده‌تر:** به‌جای شماره‌ی صحیح ساده، از جدیدترین `date_modified_gmt` در میان محصولات/سفارش‌ها به‌عنوان «نسخه» استفاده شود.
2. **راه دقیق‌تر و پیشنهادی:** یک افزونه‌ی همراه سبک روی وردپرس ساخته شود که با قلاب‌شدن (hook) به رویدادهای تغییر محصول/سفارش/موجودی، یک شمارنده‌ی صحیح را در دیتابیس وردپرس بالا ببرد و از طریق یک endpoint اختصاصی و بسیار سبک (`GET /wp-json/woogit/v1/version`) در دسترس اپ بگذارد. این افزونه طبق بخش لایسنس باید GPLv2+ باشد.

### ۶. سفارش‌ها: دو لایه‌ی تجربه و مدیریت

#### لایه اول — خلاصه و دسترسی سریع

این لایه برای **اسکن سریع و فهم فوری سفارش** طراحی می‌شود. اطلاعات کلیدی باید بدون ورود به جزئیات قابل مشاهده باشند، از جمله:

- شماره سفارش
- تاریخ سفارش
- مبلغ سفارش
- تعداد اقلام
- وضعیت سفارش

هدف این لایه این است که کاربر بتواند در کمترین زمان بفهمد چه سفارشی است و وضعیت کلی آن چیست.

#### لایه دوم — جزئیات کامل و مدیریت سفارش

با ورود به جزئیات، اطلاعات کامل سفارش در دسترس باشد؛ از جمله اطلاعات مشتری، محصولات و تعداد و قیمت آن‌ها، آدرس، شماره تماس، مبلغ‌ها و تخفیف‌ها، روش پرداخت، روش حمل‌ونقل، یادداشت‌های مشتری/مدیر، وضعیت پرداخت و ارسال، کد یا اطلاعات رهگیری و سایر اطلاعات مرتبطی که WooCommerce برای سفارش در اختیار قرار می‌دهد.

علاوه بر مشاهده، **تمام عملیات مدیریتی لازم برای سفارش** نیز در این لایه قرار می‌گیرد؛ از جمله تغییر وضعیت سفارش، مدیریت وضعیت پرداخت و ارسال، افزودن/ویرایش یادداشت، تغییر اقلام و تعداد، تغییر اطلاعات مشتری و آدرس، لغو یا بازگردانی سفارش و سایر عملیات مدیریتی قابل انجام در WooCommerce.

اصل طراحی: **لایه اول برای سرعت است؛ لایه دوم برای کامل بودن.** این دو هدف نباید با یکدیگر قاطی شوند و باعث سنگین شدن نمای اولیه سفارش شوند.

### ۷. مدیریت محصولات — جایگزین عملی مدیریت محصولات WooCommerce

محور سوم WooGit باید در نهایت بتواند **تقریباً جایگزین کامل بخش مدیریت محصولات WooCommerce** باشد تا کاربر برای مدیریت محصولات جدید و موجود، تا حد ممکن نیازی به ورود به پنل WordPress/WooCommerce نداشته باشد.

دامنه‌ی مدیریت محصول باید شامل موارد زیر باشد:

- افزودن محصول جدید
- ویرایش محصول موجود
- نام محصول و توضیحات
- قیمت عادی و قیمت تخفیف‌خورده
- موجودی و مدیریت Stock
- دسته‌بندی‌ها
- تصویر اصلی محصول و گالری تصاویر
- ویژگی‌ها و مشخصات محصول
- وضعیت انتشار و وضعیت محصول
- محصولات ساده
- محصولات متغیر و Variationها
- مدیریت اطلاعات و قیمت/موجودی Variationها
- حذف محصول
- و سایر امکانات ضروری مدیریت محصول که WooCommerce در اختیار مدیر فروشگاه قرار می‌دهد.

**اصل UX این بخش:** اگرچه دامنه‌ی امکانات کامل است، مسیر انجام کار نباید به اندازه‌ی پنل WordPress پیچیده و سنگین شود. کاربر باید بتواند عملیات پرتکرار را با سریع‌ترین مسیر ممکن انجام دهد و امکانات پیچیده‌تر بدون ایجاد شلوغی در مسیر اصلی در دسترس باشند.

این بخش از نظر فوریت بعد از اعلان سفارش و مدیریت سفارش قرار دارد، اما **سرعت انجام کار در لحظه‌ی نیاز همچنان یک معیار اصلی موفقیت آن است.**

### ۸. اعلان سفارش جدید (New Order Notification) — قابلیت حیاتی نسخه‌ی اول

اعلان سفارش جدید یک قابلیت فرعی یا صرفاً یک Notification ساده نیست؛ **یکی از ستون‌های اصلی WooGit و اولین نقطه‌ی تماس کاربر با محصول است.**

الزامات اصلی این قابلیت:

- کاربر باید بتواند **حتی زمانی که برنامه کاملاً بسته است**، اعلان سفارش جدید را دریافت کند.
- اعلان باید تا حد امکان سریع و قابل‌اعتماد باشد و هدف عملی آن اطلاع‌رسانی در مقیاس **دقیقه** باشد؛ تأخیر طولانی که کاربر را مجبور به بررسی دستی سایت کند قابل قبول نیست و حداکثر قابل‌قبول حدود یک ساعت است.
- اعلان باید اطلاعات مفید و کوتاهی از سفارش داشته باشد؛ مانند **شماره سفارش، مبلغ سفارش و اطلاعات ضروری قابل نمایش در Notification**.
- با لمس اعلان، کاربر باید بتواند **مستقیماً وارد صفحه‌ی جزئیات همان سفارش** شود.
- دریافت اعلان نباید وابسته به باز بودن اپ یا اجرای دائمی اپ در پس‌زمینه باشد.
- معماری اعلان باید با مدل آفلاین‌محور و Core مشترک سازگار باشد.
- چون REST API ووکامرس ذاتاً pull-based است، برای این قابلیت باید از **WooCommerce Webhooks** و/یا یک مکانیزم Push مناسب استفاده شود؛ polling مداوم از اپ نباید راهکار اصلی اعلان باشد.
- سیستم Notification باید از ابتدا طوری طراحی شود که در آینده بتواند قابلیت‌هایی مانند دسته‌بندی اعلان‌ها، اعلان تغییر وضعیت سفارش و تنظیمات اعلان را بدون بازطراحی اساسی پشتیبانی کند.

> **اصل مهم:** «اعلان سفارش جدید» باید از نظر فوریت و قابلیت اطمینان، بالاترین سطح اولویت در میان قابلیت‌های ارتباطی WooGit داشته باشد.

### ۹. مسیر تجاری‌سازی و بیلینگ (برای آینده)

از آن‌جا که مخاطب اصلی داخل ایران است، **تکیه‌ی صرف بر Google Play Billing کافی نیست**. معماری بیلینگ باید از ابتدا **چندگانه و قابل تعویض (Pluggable Billing)** طراحی شود:

- یک لایه‌ی انتزاعی برای «پرداخت/اشتراک» در هسته تعریف شود که پیاده‌سازی واقعی‌اش می‌تواند یکی از این‌ها باشد:
  - **Google Play Billing**
  - **کافه‌بازار (Cafe Bazaar IAB)** و **مایکت (Myket IAB)**
  - **درگاه‌های پرداخت مستقیم ایرانی** مثل زرین‌پال، زیبال، آیدی‌پی، پی‌پینگ
- انتخاب روش پرداخت باید config قابل تغییر باشد، نه چیزی که به بازنویسی نیاز داشته باشد.
- برای مدیریت لایسنس/اشتراک کاربران در مقیاس چندفروشگاهی، یک بک‌اند سبک برای تأیید و مدیریت اشتراک لازم خواهد بود؛ داده‌های فروشگاه‌ها همچنان روی هاست خود کاربر باقی می‌مانند.

### ۱۰. رابط کاربری: تم Liquid Glass

نمای کلی اپ باید از سبک طراحی **Liquid Glass** (شیشه‌ی مایع — سبک طراحی شفاف/لایه‌ای با بلور و نور، مشابه جدیدترین زبان طراحی اپل) پیروی کند:
- لایه‌های نیمه‌شفاف با افکت بلور پشت زمینه (Backdrop Blur)
- سایه‌ها و هایلایت‌های نرم برای حس شیشه‌ای بودن و عمق
- انیمیشن‌های نرم و روان هنگام جابه‌جایی بین لایه‌ها
- در Jetpack Compose این جلوه از طریق ترکیب `Modifier.blur`، شفافیت رنگی (alpha)، و گرادیان‌های ظریف قابل پیاده‌سازی است؛ باید یک سیستم طراحی اختصاصی برای این تم در ابتدای کار تعریف شود.

### ۱۱. آماده‌بودن برای آینده (Future-Proofing)

ساختار پروژه از روز اول باید طوری باشد که افزودن موارد زیر بدون بازطراحی اساسی ممکن باشد:
- **پشتیبانی از هوش مصنوعی** — از طریق ماژول جداگانه‌ی `ai`
- **iOS** — از طریق هسته‌ی مشترک KMP؛ فقط لایه‌ی UI (SwiftUI) بعداً اضافه می‌شود
- **به‌روزرسانی هسته** — نسخه‌بندی مشخص برای ماژول Core
- **درگاه‌های پرداخت جدید** — از طریق لایه‌ی انتزاعی بیلینگ
- **گسترش سیستم اعلان‌ها** — مانند اعلان تغییر وضعیت سفارش، اعلان‌های قابل تنظیم و دسته‌بندی اعلان‌ها

### ۱۲. نکات فنی و محدودیت‌های شناخته‌شده‌ی API ووکامرس

این‌ها باید در طراحی و پیاده‌سازی در نظر گرفته شوند:

- ارسال دسته‌جمعی (batch) از طریق `POST /wp-json/wc/v3/products/batch` با کلیدهای `create` / `update` / `delete` انجام می‌شود.
- محدودیت پیش‌فرض هر درخواست batch **۱۰۰ آیتم** است.
- آپلود تصویر محصول در batch API انجام نمی‌شود؛ باید ابتدا تصویر به `wp-json/wp/v2/media` آپلود و سپس به محصول متصل شود.
- REST API ووکامرس ذاتاً **pull-based** است، نه push. برای اطلاع لحظه‌ای از رویدادهایی مثل سفارش جدید، باید از **WooCommerce Webhooks** استفاده شود.
- احراز هویت برای یک فروشگاه: Consumer Key/Secret. برای نسخه‌ی چندفروشگاهی آینده نیاز به مدیریت چند اتصال هم‌زمان خواهد بود.
- سرعت واقعی همگام‌سازی به قدرت هاست فروشگاه وابسته است و باید timeout، retry و مدیریت خطا در نظر گرفته شود.

### ۱۳. آنچه هنوز باید مشخص شود (برای جلسات بعدی)

- طراحی دقیق UI/UX صفحه‌ی افزودن سریع محصول (چند لمس، چه فیلدهایی الزامی)
- مشخصات کامل مدیریت محصولات و سطح پشتیبانی از محصولات ساده، متغیر و Variationها
- نحوه‌ی دقیق نمایش صف تغییرات pending و مدیریت تعارض (conflict)
- طراحی دقیق مدل Premium و کانال توزیع
- استراتژی retry و مدیریت خطا برای Batch Sync ناموفق
- تعریف دقیق سیستم طراحی Liquid Glass
- انتخاب نهایی بین Room و SQLDelight برای دیتابیس محلی در معماری KMP
- تعیین دقیق محتوای اعلان سفارش جدید، اکشن‌های داخل اعلان و سطح کنترل کاربر روی اعلان‌ها
