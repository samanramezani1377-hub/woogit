# WooGit

اپلیکیشن اندرویدی اختصاصی برای مدیریت سریع و آفلاین‌محور فروشگاه‌های ووکامرس، با مدل همگام‌سازی شبیه به `git push`.

---

## پرامپت پروژه (Project Prompt)

> این بخش یک شرح کامل و دقیق از چیزی است که باید ساخته شود. هر بار که قرار است روی این پروژه (توسط انسان یا مدل هوش مصنوعی) کار شود، باید این پرامپت به‌طور کامل خوانده شود.

> **قاعده‌ی تفسیر «آینده» در این سند:** هر جا در این پرامپت یا در جلسات بعدی گفته شود که قابلیتی «در آینده» اضافه می‌شود، منظور این است که **هسته (Core) باید از همین حالا برای پذیرفتن آن قابلیت آماده و باز طراحی شده باشد** (مثلاً ماژول جدا، لایه‌ی انتزاعی، اینترفیس مشخص)، اما **پیاده‌سازی و فعال‌سازی واقعی آن قابلیت به نسخه‌های بعدی موکول می‌شود** و بخشی از نسخه‌ی یک نیست.

### ۱. مشکل اصلی

اپلیکیشن‌های موجود برای مدیریت ووکامرس روی اندروید (اپ رسمی WooCommerce/WordPress، و اپ‌های ثالث مثل Hippoo) کند، سنگین، و از نظر تجربه‌ی کاربری ضعیف هستند. هدف ساخت یک اپلیکیشن اختصاصی، سریع و ساده است که دقیقاً مطابق نیاز واقعی مدیریت یک فروشگاه ساخته شده باشد، نه یک ابزار همه‌کاره‌ی شلوغ.

### ۲. سه محور اصلی محصول و الگوی استفاده

WooGit قرار نیست صرفاً یک اپ دیگر برای مشاهده‌ی WooCommerce باشد. هدف اصلی آن ساخت یک ابزار مدیریتی سریع و تخصصی برای صاحب فروشگاه است تا برای سه کار اصلی فروشگاه، تا جای ممکن از پنل WordPress/WooCommerce بی‌نیاز شود.

**سه محور زیر هسته و اصل محصول هستند و نباید به‌عنوان قابلیت‌های فرعی یا قابل حذف در نظر گرفته شوند:**

1. **اعلان سفارش جدید — محور فوری (Immediate):** اولین و فوری‌ترین نقطه‌ی تماس کاربر با WooGit. کاربر باید حتی وقتی برنامه کاملاً بسته است، در سریع‌ترین زمان ممکن از ثبت سفارش جدید مطلع شود. هدف عملی این قابلیت اطلاع‌رسانی در مقیاس دقیقه است و در بدترین حالت قابل‌قبول نباید به تأخیری بیشتر از حدود یک ساعت وابسته باشد.
2. **مشاهده و مدیریت سفارش — محور نیاز معمول و روزانه (Hourly / Daily):** پس از دریافت اعلان، کاربر باید بتواند سفارش را داخل برنامه بررسی و مدیریت کند. این بخش ممکن است از چند بار در روز تا استفاده‌ی ساعتی یا روزانه مورد نیاز باشد و باید تا جای ممکن جایگزین پنل سفارشات WordPress/WooCommerce شود.
3. **افزودن و اصلاح محصولات — محور کم‌فوریت‌تر اما سرعت‌محور (Daily / Weekly / On-demand):** این بخش ممکن است برای کاربر روزانه، چند بار در هفته یا فقط هفته‌ای یک‌بار مورد استفاده قرار بگیرد. اما هر زمان کاربر به آن نیاز دارد، کار باید با سریع‌ترین زمان ممکن، کمترین تعداد لمس و کمترین اصطکاک انجام شود. هدف این بخش نیز بی‌نیازی عملی از مدیریت محصولات در پنل WordPress است.

این سه محور فوریت یکسانی ندارند؛ بنابراین **فوریت، زمان پاسخ، UX، اعلان، همگام‌سازی و اولویت منابع باید متناسب با الگوی واقعی استفاده‌ی هر محور طراحی شوند.**

#### اصل اولویت سه محور

- **سفارش جدید:** بالاترین فوریت؛ اطلاع‌رسانی سریع و قابل‌اعتماد حتی در حالت کاملاً بسته‌ی اپ.
- **سفارش‌ها:** نیاز معمول و روزانه؛ دسترسی سریع به خلاصه، جزئیات کامل و عملیات مدیریتی.
- **محصولات:** فوریت پایین‌تر نسبت به دو محور اول، اما سرعت انجام کار در لحظه‌ی نیاز باید بسیار بالا باشد.

### ۳. اولویت‌های بعدی پروژه

سه محور بالا اصل محصول هستند. تمام قابلیت‌ها و تصمیم‌هایی که پیش‌تر در پروژه تعریف شده‌اند **حذف نمی‌شوند**؛ بلکه در رده‌ی اهمیت و الزامات بعدی قرار می‌گیرند و باید در معماری از ابتدا برای آن‌ها آماده بود.

۱. **سرعت اصلاح و افزودن محصول جدید** — معیار اصلی موفقیت در محور سوم است. باز کردن اپ، افزودن یا ویرایش یک محصول، باید در کمترین زمان و کمترین تعداد لمس ممکن انجام شود.

۲. **حداکثر کار در داخل خود اپ** — هدف معماری این است که کاربر برای سه محور اصلی و عملیات مرتبط با آن‌ها، تا جای ممکن نیاز به باز کردن مرورگر یا پنل وردپرس نداشته باشد.

۳. **مدل همگام‌سازی شبیه به `git push`** — تمام تغییرات (محصول جدید، ویرایش، تغییر موجودی/قیمت، تغییر وضعیت سفارش) ابتدا **به‌صورت محلی و آفلاین** ذخیره و در UI فوراً اعمال می‌شوند (Optimistic UI). سپس با یک حرکت (خودکار در پس‌زمینه یا با یک دکمه‌ی صریح شبیه "Push") تمام تغییرات ذخیره‌شده یک‌جا به ووکامرس ارسال می‌شوند. کاربر نباید منتظر پاسخ سرور برای هر تغییر کوچک بماند.

۴. **سرعت اجرای اپ در حد اپ‌های بسیار سریع و بهینه‌ی بازار** — تجربه‌ی کاربری باید native و روان باشد، بدون تأخیر، بدون لگ، شبیه بهترین اپ‌های موجود در Google Play از نظر سرعت رندر و پاسخ‌دهی.

۵. **قابلیت تبدیل بعدی به یک محصول تجاری (Productization)** — معماری باید از ابتدا به‌گونه‌ای طراحی شود که بتوان بعداً آن را برای چندین فروشگاه/چندین کاربر عرضه کرد، مدل Freemium/Premium پیاده‌سازی کرد و بدون بازنویسی اساسی مقیاس‌پذیر باشد.

### ۴. معماری فنی پیشنهادی

**اصل بنیادین: ساخت از «هسته» به بیرون (Core-Out Architecture).** پروژه نباید مستقیم از UI اندروید شروع شود. باید یک **هسته‌ی مشترک (Core Module)** مستقل از پلتفرم ساخته شود که شامل تمام منطق تجاری، مدل‌های دامنه، موتور همگام‌سازی (Sync Engine)، صف تغییرات، و ارتباط با REST API ووکامرس باشد. لایه‌های بیرونی فقط مصرف‌کننده‌ی این هسته هستند.

- **رویکرد Multiplatform:** استفاده از **Kotlin Multiplatform (KMP)** برای دامنه، شبکه، دیتابیس محلی و Sync تا iOS در آینده بدون بازنویسی منطق تجاری قابل اضافه شدن باشد.
- **UI اندروید:** Jetpack Compose (Material 3) با تم اختصاصی Liquid Glass.
- **معماری لایه‌ای:** Clean Architecture با جداسازی سخت‌گیرانه‌ی Core از UI.
- **دیتابیس محلی/صف تغییرات:** SQLDelight یا Room با پشتیبانی KMP؛ تمام تغییرات ابتدا محلی ذخیره می‌شوند.
- **ارتباط شبکه:** Ktor Client برای REST API ووکامرس.
- **همگام‌سازی پس‌زمینه:** WorkManager در اندروید.
- **تزریق وابستگی:** Koin یا Hilt، بسته به سازگاری با KMP.
- **Async:** Kotlin Coroutines & Flow.
- **ماژول جداگانه‌ی AI:** از ابتدا یک ماژول `ai` یا `assistant` برای قابلیت‌های آینده مانند پیشنهاد قیمت، تولید توضیحات و تحلیل فروش.
- بدون نیاز به سرور اختصاصی برای هسته‌ی اصلی؛ خود WordPress/WooCommerce بک‌اند است.

### ۵. مکانیزم نسخه‌بندی داده (Data Versioning / «شماره کامیت»)

این مکانیزم بخشی از هسته‌ی نسخه‌ی یک است و برای سرعت، آفلاین‌بودن و تجربه‌ی کاربری استفاده می‌شود. یک شماره نسخه‌ی سراسری شبیه شماره کامیت برای داده‌های فروشگاه نگه‌داری می‌شود. اپ داده‌ها را محلی نگه می‌دارد و ابتدا فقط شماره نسخه را بررسی می‌کند؛ در صورت تفاوت، همگام‌سازی انجام می‌شود.

**تصمیم نهایی:** نسخه اول از `date_modified_gmt` ووکامرس به‌عنوان نسخه سمت سرور استفاده می‌کند (بدون نیاز به افزونه یا بک‌اند اضافی). ساخت افزونه‌ی همراه سبک با endpoint اختصاصی مانند `GET /wp-json/woogit/v1/version` برای Commit واقعی و دقیق‌تر به نسخه‌های آینده موکول شده است. جزئیات کامل در `docs/CONNECTION_AND_SYNC.md` و `docs/COMMIT_VERSIONING.md`.

### ۶. سفارش‌ها: دو لایه‌ی تجربه و مدیریت

#### لایه اول — خلاصه و دسترسی سریع

شماره سفارش، تاریخ، مبلغ، تعداد اقلام و وضعیت سفارش باید در یک نگاه قابل مشاهده باشند.

#### لایه دوم — جزئیات کامل و مدیریت سفارش

تمام اطلاعات سفارش مانند مشتری، محصولات، تعداد و قیمت، آدرس، تماس، مبالغ و تخفیف‌ها، روش پرداخت، حمل‌ونقل، یادداشت‌ها، وضعیت پرداخت/ارسال و رهگیری در دسترس باشد.

تمام عملیات مدیریتی لازم نیز در همین لایه قرار می‌گیرد؛ از جمله تغییر وضعیت، مدیریت پرداخت و ارسال، یادداشت، تغییر اقلام و تعداد، تغییر اطلاعات مشتری و آدرس، لغو/بازگردانی و سایر عملیات WooCommerce.

**اصل طراحی:** لایه اول برای سرعت است و لایه دوم برای کامل بودن.

### ۷. مدیریت محصولات — جایگزین کامل مدیریت محصولات WooCommerce

محور سوم WooGit باید در نهایت از نظر مدیریت محصول، تا حد امکان **جایگزین کامل بخش Products در WooCommerce** باشد و کاربر برای مدیریت معمول محصولات مجبور به باز کردن پنل WordPress نباشد.

این بخش باید از ابتدا برای موارد زیر آماده باشد:

- افزودن محصول جدید
- ویرایش محصول
- نام، توضیحات و اطلاعات اصلی
- قیمت عادی و تخفیف
- موجودی و مدیریت Stock
- دسته‌بندی
- تصویر اصلی و گالری تصاویر
- ویژگی‌ها و مشخصات
- وضعیت انتشار
- محصولات ساده
- محصولات متغیر و Variationها
- حذف محصول
- و سایر عملیات اصلی قابل انجام روی محصول در WooCommerce

**اصل UX این بخش:** کامل بودن امکانات نباید باعث کند شدن مسیرهای پرتکرار شود. مسیر «افزودن سریع» و «اصلاح سریع» باید کوتاه‌ترین و سریع‌ترین مسیر ممکن باشد و قابلیت‌های پیشرفته در لایه‌ها/صفحات بعدی در دسترس قرار گیرند.

### ۸. داشبورد و صفحه اصلی

صفحه اصلی WooGit باید یک **داشبورد عملیاتی** باشد، نه صرفاً یک صفحه‌ی منوی امکانات. در اولین نگاه، کاربر باید بتواند وضعیت مهم فروشگاه را ببیند و سریع به سه محور اصلی دسترسی پیدا کند.

اجزای اصلی داشبورد شامل:

- 🔔 سفارش‌های جدید و خوانده‌نشده
- 📦 سفارش‌های اخیر
- 🛍️ دسترسی سریع به مدیریت محصولات
- ➕ میانبر «افزودن سریع محصول»
- اطلاعات/آمار کاربردی فروشگاه در صورت نیاز

داشبورد باید طوری طراحی شود که کاربر برای رسیدن به عملیات اصلی، حداقل تعامل را انجام دهد. با این حال، **اعلان سفارش جدید همچنان مهم‌ترین نقطه تماس فوری محصول است** و داشبورد نباید جایگزین Notification شود.

### ۹. آمادگی برای چندفروشگاهی (Multi-Store Ready)

**نسخه فعلی برای یک فروشگاه WooCommerce طراحی می‌شود** و تجربه‌ی کاربری و جریان اصلی نباید به‌خاطر چندفروشگاهی شدن زودهنگام پیچیده شود.

با این حال، Core و مدل داده از ابتدا باید **Multi-Store Ready** باشند؛ یعنی اتصال فروشگاه یک موجودیت مستقل و قابل توسعه باشد و داده‌ها، تنظیمات، احراز هویت، Sync، اعلان‌ها و صف تغییرات بتوانند در آینده به تفکیک چند فروشگاه مدیریت شوند.

در آینده، کاربر باید بتواند چند فروشگاه WooCommerce را به یک WooGit متصل کند و از داخل یک اپ بین آن‌ها جابه‌جا شود.

مهم‌تر از آن، داشبورد اصلی در حالت چندفروشگاهی باید بتواند **سفارش‌های جدید چند فروشگاه را به‌صورت یکجا** در بخش اصلی «سفارش‌های جدید» نمایش دهد؛ به‌گونه‌ای که کاربر بدون ورود جداگانه به هر فروشگاه، در یک نگاه متوجه شود کدام فروشگاه سفارش جدید دارد و بتواند مستقیماً همان سفارش را باز کند.

در طراحی این قابلیت باید شناسه/نام فروشگاه به‌وضوح کنار سفارش نمایش داده شود تا سفارش‌های فروشگاه‌های مختلف با یکدیگر اشتباه نشوند.

**اصل مهم:** Multi-Store قابلیت آینده است، اما آماده‌سازی معماری آن از امروز الزامی است؛ پیاده‌سازی کامل چندفروشگاهی می‌تواند به نسخه‌ی بعدی موکول شود.

### ۱۰. اعلان سفارش جدید (New Order Notification) — قابلیت حیاتی نسخه‌ی اول

کاربر باید حتی وقتی برنامه کاملاً بسته است اعلان سفارش جدید را دریافت کند. هدف اطلاع‌رسانی در مقیاس دقیقه و حداکثر قابل‌قبول حدود یک ساعت است. اعلان باید اطلاعات کوتاه و مفید مانند شماره سفارش و مبلغ را نشان دهد و با لمس آن مستقیماً به جزئیات همان سفارش برود. دریافت اعلان نباید به باز بودن اپ یا اجرای دائمی آن وابسته باشد. برای Push باید از Webhooks و/یا مکانیزم مناسب استفاده شود و polling مداوم راهکار اصلی نباشد.

در معماری آینده‌ی Multi-Store، هر Notification باید **منبع/فروشگاه مربوط به خود را نیز مشخص کند** تا اگر چند فروشگاه به یک اپ متصل بودند، اعلان و Deep Link دقیقاً به فروشگاه و سفارش صحیح هدایت شوند.

### ۱۱. مسیر تجاری‌سازی و بیلینگ (برای آینده)

معماری بیلینگ باید Pluggable باشد تا Google Play Billing، کافه‌بازار، مایکت و درگاه‌های مستقیم ایرانی مانند زرین‌پال، زیبال، آیدی‌پی و پی‌پینگ قابل پشتیبانی باشند. مدیریت اشتراک چندفروشگاهی در آینده می‌تواند به یک بک‌اند سبک برای لایسنس محدود شود و داده‌های فروشگاه‌ها روی هاست خود کاربر باقی بمانند.

### ۱۲. رابط کاربری: تم Liquid Glass

نمای کلی اپ باید از سبک Liquid Glass با لایه‌های نیمه‌شفاف، بلور، سایه‌های نرم و انیمیشن‌های روان پیروی کند و یک Design System اختصاصی برای آن تعریف شود.

### ۱۳. آماده‌بودن برای آینده (Future-Proofing)

ساختار پروژه باید از روز اول برای AI، iOS از طریق KMP، نسخه‌بندی Core، درگاه‌های پرداخت جدید، گسترش سیستم اعلان‌ها و Multi-Store آماده باشد.

### ۱۴. نکات فنی و محدودیت‌های شناخته‌شده‌ی API ووکامرس

- Batch API محصولات با `create` / `update` / `delete` کار می‌کند.
- محدودیت پیش‌فرض batch معمولاً ۱۰۰ آیتم است.
- آپلود تصویر محصول باید جدا از Batch انجام شود.
- REST API ووکامرس pull-based است؛ برای رویداد سفارش جدید Webhook مناسب‌تر است.
- احراز هویت فروشگاه با Consumer Key/Secret انجام می‌شود.
- Sync باید timeout، retry و مدیریت خطا داشته باشد.

- مدل دقیق چند دستگاه/چند کاربر و سطح دسترسی برای آینده (پرسش ۰۸ — فعلاً غیرفعال تا رسیدن به مرحله طراحی آن بخش)
- مدل Premium و کانال توزیع/بیلینگ
- انتخاب نهایی بین Room یا SQLDelight برای دیتابیس محلی
- مدل دقیق Account/Store برای حالت Multi-Store آینده
- نحوه‌ی تجمیع، فیلتر و Deep Link سفارش‌های چند فروشگاه در داشبورد آینده
- تولید واقعی Design System و طراحی Hi-Fi تمام صفحات (طبق تصمیم پرسش ۱۳، این طراحی باید پیش از شروع کدنویسی آماده شود؛ خود فایل/محصول طراحی هنوز ساخته نشده است)

برای فهرست کامل تصمیمات قطعی و جزئیات هرکدام، به `docs/DECISION_TRACKER.md` مراجعه شود.
