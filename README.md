# WooGit

اپلیکیشن اندرویدی اختصاصی برای مدیریت سریع و آفلاین‌محور فروشگاه‌های ووکامرس، با مدل همگام‌سازی شبیه به `git push`.

---

## پرامپت پروژه (Project Prompt)

> این بخش یک شرح کامل و دقیق از چیزی است که باید ساخته شود. هر بار که قرار است روی این پروژه (توسط انسان یا مدل هوش مصنوعی) کار شود، باید این پرامپت به‌طور کامل خوانده شود.

> **قاعده‌ی تفسیر «آینده» در این سند:** هر جا در این پرامپت یا در جلسات بعدی گفته شود که قابلیتی «در آینده» اضافه می‌شود، منظور این است که **هسته (Core) باید از همین حالا برای پذیرفتن آن قابلیت آماده و باز طراحی شده باشد** (مثلاً ماژول جدا، لایه‌ی انتزاعی، اینترفیس مشخص)، اما **پیاده‌سازی و فعال‌سازی واقعی آن قابلیت به نسخه‌های بعدی موکول می‌شود** و بخشی از نسخه‌ی یک نیست.

### ۱. مشکل اصلی

اپلیکیشن‌های موجود برای مدیریت ووکامرس روی اندروید (اپ رسمی WooCommerce/WordPress، و اپ‌های ثالث مثل Hippoo) کند، سنگین، و از نظر تجربه‌ی کاربری ضعیف هستند. هدف ساخت یک اپلیکیشن اختصاصی، سریع و ساده است که دقیقاً مطابق نیاز واقعی مدیریت یک فروشگاه ساخته شده باشد، نه یک ابزار همه‌کاره‌ی شلوغ.

### ۲. اولویت‌های اصلی (به ترتیب اهمیت)

۱. **سرعت اصلاح و افزودن محصول جدید** — مهم‌ترین معیار موفقیت پروژه است. باز کردن اپ، افزودن یا ویرایش یک محصول، باید در کمترین زمان و کمترین تعداد لمس ممکن انجام شود.

۲. **حداکثر کار در داخل خود اپ** — کاربر نباید برای کارهای روزمره (مدیریت سفارش، ویرایش محصول، موجودی، قیمت) نیاز به باز کردن مرورگر یا پنل وردپرس داشته باشد.

۳. **مدل همگام‌سازی شبیه به `git push`** — تمام تغییرات (محصول جدید، ویرایش، تغییر موجودی/قیمت، تغییر وضعیت سفارش) ابتدا **به‌صورت محلی و آفلاین** ذخیره و در UI فوراً اعمال می‌شوند (Optimistic UI). سپس با یک حرکت (خودکار در پس‌زمینه یا با یک دکمه‌ی صریح شبیه "Push") تمام تغییرات ذخیره‌شده یک‌جا به ووکامرس ارسال می‌شوند. کاربر نباید منتظر پاسخ سرور برای هر تغییر کوچک بماند.

۴. **سرعت اجرای اپ در حد اپ‌های بسیار سریع و بهینه‌ی بازار** — تجربه‌ی کاربری باید native و روان باشد، بدون تأخیر، بدون لگ، شبیه بهترین اپ‌های موجود در Google Play از نظر سرعت رندر و پاسخ‌دهی.

۵. **قابلیت تبدیل بعدی به یک محصول تجاری (Productization)** — معماری باید از ابتدا به‌گونه‌ای طراحی شود که بتوان بعداً:
   - آن را برای چندین فروشگاه/چندین کاربر عرضه کرد
   - یک مدل **Freemium/Premium** پیاده‌سازی کرد (برخی امکانات رایگان، برخی پولی)
   - بدون بازنویسی اساسی، مقیاس‌پذیر باشد

### ۳. معماری فنی پیشنهادی

**اصل بنیادین: ساخت از «هسته» به بیرون (Core-Out Architecture).**
پروژه نباید مستقیم از UI اندروید شروع شود. باید یک **هسته‌ی مشترک (Core Module)** مستقل از پلتفرم ساخته شود که شامل تمام منطق تجاری، مدل‌های دامنه، موتور همگام‌سازی (Sync Engine)، صف تغییرات، و ارتباط با REST API ووکامرس باشد. لایه‌های بیرونی (UI اندروید، و بعداً UI آی‌فون) فقط مصرف‌کننده‌ی این هسته هستند. مزیت این رویکرد:
- وقتی هسته آپدیت یا اصلاح می‌شود (باگ‌فیکس، قابلیت جدید، بهبود موتور Sync)، این تغییر خودکار به تمام پلتفرم‌ها می‌رسد.
- افزودن قابلیت‌های آینده (پشتیبانی هوش مصنوعی، گیت‌وی‌های پرداخت جدید، منطق جدید کسب‌وکار) در هسته انجام می‌شود و تنها یک بار پیاده‌سازی می‌شود.

- **رویکرد Multiplatform:** به‌جای نوشتن هسته فقط برای اندروید، از **Kotlin Multiplatform (KMP)** استفاده شود. لایه‌ی هسته (دامنه، شبکه، دیتابیس محلی، موتور Sync) با KMP نوشته می‌شود تا هم اندروید و هم (در آینده) iOS بتوانند مستقیماً از همان کد استفاده کنند، بدون بازنویسی منطق تجاری. این دقیقاً همان آماده‌بودن برای iOS است که خواسته شده — فعلاً فقط لایه‌ی UI اندروید (Compose) روی این هسته ساخته می‌شود؛ لایه‌ی UI iOS (SwiftUI) هر وقت لازم شد بدون دست‌زدن به هسته اضافه می‌شود.
- **UI اندروید:** Jetpack Compose (Material 3) — با تم اختصاصی «Liquid Glass» (بخش ۷)
- **معماری لایه‌ای:** Clean Architecture (Core مشترک KMP + لایه‌ی Presentation مخصوص هر پلتفرم)، مشابه رویکرد پروژه‌ی ZeroGram اما با جداسازی سخت‌گیرانه‌تر هسته از UI
- **دیتابیس محلی/صف تغییرات:** SQLDelight یا Room با پشتیبانی KMP — تمام تغییرات کاربر ابتدا اینجا ذخیره می‌شوند (منبع حقیقت آفلاین)
- **ارتباط شبکه:** Ktor Client (سازگار با KMP) برای صحبت با REST API ووکامرس (`wp-json/wc/v3/...`)
- **همگام‌سازی پس‌زمینه:** WorkManager در اندروید (فراخوانی منطق Sync از هسته‌ی مشترک)
- **تزریق وابستگی:** Koin یا Hilt (بسته به سازگاری با KMP)
- **Async:** Kotlin Coroutines & Flow
- **ماژول جداگانه برای هوش مصنوعی:** از همین ابتدا یک ماژول (حتی خالی/placeholder) به اسم `ai` یا `assistant` در نظر گرفته شود تا وقتی قابلیت‌های هوش مصنوعی (مثلاً پیشنهاد قیمت، تولید توضیحات محصول، تحلیل فروش) اضافه شدند، به هسته‌ی اصلی وصل شوند بدون تغییر ساختار کلی.
- بدون نیاز به سرور اختصاصی برای هسته‌ی اصلی — خود وردپرس/ووکامرس نقش بک‌اند را دارد. (سرور جدا فقط برای لایسنس/پرمیوم طبق بخش ۶)

### ۴. مکانیزم نسخه‌بندی داده (Data Versioning / «شماره کامیت»)

> این مکانیزم بخشی از هسته‌ی نسخه‌ی یک است، نه یک قابلیت آینده — چون مستقیماً به اولویت اول پروژه (سرعت) وابسته است.

ایده: یک شماره‌ی نسخه‌ی سراسری (شبیه به شماره‌ی کامیت در گیت) برای داده‌های فروشگاه نگه‌داری شود:

- هر بار داده‌ای در سایت تغییر می‌کند (چه از طریق خود اپ، چه از پنل وردپرس، چه از هر منبع دیگری)، یک شماره‌ی نسخه‌ی سراسری در سمت سرور **بالا می‌رود**.
- اپ همیشه آخرین شماره‌نسخه‌ای که خودش دارد را به‌همراه داده‌ها به‌صورت محلی (کاملاً داخل گوشی) ذخیره می‌کند. تمام صفحات اپ از همین داده‌ی محلی خوانده می‌شوند، نه مستقیم از سایت.
- در دو لحظه، اپ فقط **شماره‌ی نسخه** را از سایت می‌پرسد (یک درخواست بسیار سبک، نه کل داده):
  1. در پس‌زمینه، حتی وقتی اپ بسته است (با WorkManager/کارهای دوره‌ای)
  2. لحظه‌ی باز شدن اپ (یا حتی کمی قبل از باز شدن کامل، اگر پلتفرم اجازه دهد)
- اگر شماره‌نسخه‌ی سرور با نسخه‌ی محلی یکسان بود → هیچ داده‌ای از سایت لود نمی‌شود، همان داده‌ی محلی نمایش داده می‌شود (سرعت لحظه‌ای، مطابق اولویت اول پروژه).
- اگر شماره‌نسخه فرق داشت → همگام‌سازی داده (کامل یا فقط بخش تغییریافته) در پس‌زمینه انجام می‌شود، و پس از اتمام، شماره‌نسخه‌ی محلی هم به‌روزرسانی می‌شود.
- وقتی خود اپ تغییری را «Push» می‌کند (طبق مدل بخش ۲)، بعد از موفقیت‌آمیز بودن ارسال، هم سرور شماره‌نسخه را بالا می‌برد و هم اپ نسخه‌ی محلی‌اش را هم‌گام با آن به‌روزرسانی می‌کند — دقیقاً مثل رفتار `commit` در گیت.

**نکته‌ی پیاده‌سازی:** خود API استاندارد ووکامرس چنین شماره‌ی سراسری‌ای ندارد (فقط `date_modified` روی هر آیتم دارد). دو مسیر ممکن است:
1. **راه ساده‌تر (بدون افزونه‌ی اضافه):** به‌جای شماره‌ی صحیح ساده، از جدیدترین `date_modified_gmt` در میان محصولات/سفارش‌ها به‌عنوان «نسخه» استفاده شود.
2. **راه دقیق‌تر و پیشنهادی:** یک افزونه‌ی همراه سبک روی وردپرس ساخته شود که با قلاب‌شدن (hook) به رویدادهای تغییر محصول/سفارش/موجودی، یک شمارنده‌ی صحیح را در دیتابیس وردپرس بالا ببرد و از طریق یک endpoint اختصاصی و بسیار سبک (`GET /wp-json/woogit/v1/version`) در دسترس اپ بگذارد. (این افزونه طبق بخش لایسنس، چون مستقیم با هسته‌ی وردپرس یکپارچه می‌شود، باید GPLv2+ باشد.)

### ۵. نکات فنی و محدودیت‌های شناخته‌شده‌ی API ووکامرس

این‌ها باید در طراحی و پیاده‌سازی در نظر گرفته شوند:

- ارسال دسته‌جمعی (batch) از طریق `POST /wp-json/wc/v3/products/batch` با کلیدهای `create` / `update` / `delete` انجام می‌شود.
- محدودیت پیش‌فرض هر درخواست batch **۱۰۰ آیتم** است (قابل افزایش با فیلتر سمت سرور `woocommerce_api_bulk_limit`، چون هاست فروشگاه در اختیار خودمان است).
- آپلود تصویر محصول در batch API انجام نمی‌شود؛ باید دو مرحله‌ای انجام شود: ابتدا آپلود عکس به `wp-json/wp/v2/media`، سپس اتصال شناسه‌ی عکس به محصول.
- REST API ووکامرس ذاتاً **pull-based** است، نه push. برای اطلاع لحظه‌ای از رویدادهایی مثل سفارش جدید، باید از **WooCommerce Webhooks** استفاده شود.
- احراز هویت برای یک فروشگاه: Consumer Key/Secret. برای نسخه‌ی چندفروشگاهی/تجاری آینده، نیاز به مکانیزم اتصال چندگانه (مثلاً OAuth یا مدیریت چند اتصال هم‌زمان) خواهد بود.
- سرعت واقعی همگام‌سازی به قدرت هاست فروشگاه وابسته است، نه فقط به کد اپ؛ در batchهای بزرگ روی هاست ضعیف احتمال timeout وجود دارد و باید مدیریت خطا/تلاش مجدد (retry) در نظر گرفته شود.

### ۶. مسیر تجاری‌سازی و بیلینگ (برای آینده)

از آن‌جا که مخاطب اصلی داخل ایران است، **تکیه‌ی صرف بر Google Play Billing کافی نیست** (هم به دلیل محدودیت‌های تحریمی و در دسترس نبودن پایدار آن برای کاربران ایرانی، هم چون توزیع اپ احتمالاً از کانال‌های داخلی هم انجام خواهد شد). معماری بیلینگ باید از ابتدا **چندگانه و قابل تعویض (Pluggable Billing)** طراحی شود:

- یک لایه‌ی انتزاعی (Abstraction) برای «پرداخت/اشتراک» در هسته تعریف شود که پیاده‌سازی واقعی‌اش می‌تواند یکی از این‌ها باشد:
  - **Google Play Billing** — برای نسخه‌ای که (اگر) از طریق گوگل‌پلی توزیع شود
  - **کافه‌بازار (Cafe Bazaar IAB)** و **مایکت (Myket IAB)** — درگاه‌های داخل‌برنامه‌ای خود این مارکت‌های ایرانی، برای نسخه‌ای که از این کانال‌ها توزیع می‌شود
  - **درگاه‌های پرداخت مستقیم ایرانی** مثل **زرین‌پال، زیبال، آیدی‌پی، پی‌پینگ** — برای پرداخت مستقیم (redirect به صفحه‌ی پرداخت وب و بازگشت به اپ)، مناسب برای APK مستقیم یا وب‌سایت
- انتخاب این‌که کدام روش برای کدام کانال توزیع فعال باشد، باید یک تنظیم (config) ساده در هسته باشد، نه چیزی که به بازنویسی نیاز داشته باشد.
- برای مدیریت لایسنس/اشتراک کاربران در مقیاس چندفروشگاهی (صرف‌نظر از این‌که کدام درگاه پرداخت استفاده شده): یک بک‌اند سبک (مثلاً Supabase یا یک سرویس کوچک Node.js) لازم است — فقط برای تأیید و مدیریت اشتراک، نه برای داده‌های فروشگاه‌ها که همچنان روی هاست خود کاربر باقی می‌مانند.
- تخمین زمان ساخت نسخه‌ی اولیه (MVP شامل: محصول، سفارش، صف آفلاین، Batch Sync): حدود ۴ تا ۸ هفته کار غیر تمام‌وقت، بر پایه‌ی تجربه‌ی پروژه‌ی مشابه (ZeroGram). این تخمین قبل از افزودن معماری Multiplatform و لایه‌ی بیلینگ چندگانه بوده و با اضافه شدن این‌ها باید بازبینی شود.

### ۷. رابط کاربری: تم Liquid Glass

نمای کلی اپ باید از سبک طراحی **Liquid Glass** (شیشه‌ی مایع — سبک طراحی شفاف/لایه‌ای با بلور و نور، مشابه جدیدترین زبان طراحی اپل) پیروی کند:
- لایه‌های نیمه‌شفاف با افکت بلور پشت زمینه (Backdrop Blur)
- سایه‌ها و هایلایت‌های نرم برای حس «شیشه‌ای بودن» و عمق
- انیمیشن‌های نرم و روان هنگام جابه‌جایی بین لایه‌ها
- در Jetpack Compose این جلوه از طریق ترکیب `Modifier.blur`، شفافیت رنگی (alpha)، و گرادیان‌های ظریف قابل پیاده‌سازی است؛ باید یک سیستم طراحی (Design System) اختصاصی برای این تم در ابتدای کار تعریف شود (رنگ‌ها، شعاع بلور، شفافیت استاندارد) تا در کل اپ یکدست اجرا شود.

### ۸. آماده‌بودن برای آینده (Future-Proofing)

ساختار پروژه از روز اول باید طوری باشد که افزودن موارد زیر بدون بازطراحی اساسی ممکن باشد:
- **پشتیبانی از هوش مصنوعی** — از طریق ماژول جداگانه‌ی `ai` که به هسته وصل می‌شود (بخش ۳)
- **iOS** — از طریق هسته‌ی مشترک KMP؛ فقط لایه‌ی UI (SwiftUI) بعداً اضافه می‌شود
- **به‌روزرسانی هسته** — نسخه‌بندی مشخص برای ماژول Core تا آپدیت‌های آن مستقل از UI پلتفرم‌ها منتشر و اعمال شوند
- **درگاه‌های پرداخت جدید** — از طریق لایه‌ی انتزاعی بیلینگ (بخش ۶)

### ۹. آنچه هنوز باید مشخص شود (برای جلسات بعدی)

- طراحی دقیق UI/UX صفحه‌ی افزودن سریع محصول (چند لمس، چه فیلدهایی الزامی)
- نحوه‌ی دقیق نمایش صف تغییرات pending به کاربر و مدیریت تعارض (conflict) در صورت تغییر هم‌زمان از پنل وردپرس
- طراحی دقیق مدل Premium (چه امکاناتی رایگان و چه چیزی پولی باشد) و این‌که کدام کانال توزیع (گوگل‌پلی/کافه‌بازار/مایکت/مستقیم) اولویت اول است
- استراتژی retry و مدیریت خطا برای Batch Sync ناموفق
- تعریف دقیق سیستم طراحی Liquid Glass (پالت رنگ، مقادیر بلور و شفافیت)
- انتخاب نهایی بین Room و SQLDelight برای دیتابیس محلی در معماری KMP
